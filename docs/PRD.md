# StoryVital — PRD (Product Requirements Document)

> **버전**: v3.0 (2026-08-01)
> **이전 버전**: [StoryVital_PRD_v2.docx](./StoryVital_PRD_v2.docx) — 5W1H/SWOT/BM 분석 포함. 본 문서는 v2를 계승하되, 제품 방향을 "창작 프로세스 가이드"에서 **"연재물 설정·인물 관리 도구"**로 재정의한 버전.

---

## 1. 제품 개요

**StoryVital**은 웹툰 작가, 웹소설 작가 등 **연재물을 만드는 스토리 창작자**를 위한 작품 관리 서비스다.

작품의 스토리와 등장인물을 디테일하게 기록하고, 고도화된 UI/UX를 통해 다음을 **직관적으로 시각화**하는 것이 핵심이다.

- 등장인물 간의 **관계**
- 등장인물 간의 **친밀도**
- **사건 발생 시간**(작중 시간선 / 타임라인)
- 각 등장인물의 **배경**(서사, 과거, 소속 등)

즉, 흩어진 설정 메모를 대체하는 단순 기록 도구가 아니라, 기록된 설정이 **관계도·타임라인 같은 시각 자료로 살아나는** 도구를 지향한다.

### 시작하게 된 문제의식 (Founding Insight)

> "요즘 재미있는 작품을 못 본 지 오래됐다. 왜일까?"

영상 퀄리티는 좋아졌는데 **스토리 개연성, 등장인물별 개연성이 무너지는 순간**("갑자기 이렇게 진행된다고?")이 몰입을 깨뜨린다. 이는 창작자의 역량 문제라기보다, **러닝타임이 길거나 연재 기간이 길어지면 창작자 스스로 설정을 까먹거나 헷갈리기 때문**이라는 가설에서 출발했다.

그렇다면 설정을 단순 텍스트(메모)로 관리하게 둘 것이 아니라, **까먹을 수 없게 시각적으로 보여주는 서비스**를 만들어 창작자에게 제공하자 — 이것이 StoryVital의 출발점이다. 기성 작가뿐 아니라 창작에 도전하는 사람들에게도 작품을 만드는 과정 자체에 도움이 되는 것을 목표로 한다.

**따라서 이 서비스의 존재 이유는 단 하나다: 창작자에게 실질적 가치가 있을 것.** 모든 기능은 "이것이 개연성 유지와 몰입도 있는 작품 완성에 기여하는가"를 기준으로 판단한다.

## 2. 아하 모먼트 (Aha Moment)

> 사용자가 "이 서비스, 계속 써야겠다"고 느끼는 결정적 순간의 정의. 온보딩과 UX의 모든 설계는 사용자를 이 순간까지 최단 경로로 데려가는 데 맞춘다.

### 핵심 아하 모먼트
**"글로만 알던 내 작품의 관계가, 한 화면에서 그림으로 보이는 순간."**

등장인물 3명과 그들의 관계를 입력하는 순간 관계도 그래프가 자동으로 그려진다. 지금까지 머릿속과 메모장에만 존재하던 인물 구도가 처음으로 시각화되는 이 순간이 StoryVital의 첫 번째 아하 모먼트다.

### 보조 아하 모먼트 (리텐션 동력)
| 순간 | 상황 | 사용자가 느끼는 것 |
|---|---|---|
| **충돌 발견** | 타임라인에 사건을 배치하다가 "이 사건이 저 사건보다 먼저면 말이 안 되는데?"를 스스로 발견 | "독자가 찾기 전에 내가 먼저 찾았다" — 연재 사고 예방 |
| **친밀도 곡선** | 회차가 쌓인 뒤 두 인물의 친밀도 변화가 그래프로 보임 | "이 커플 서사, 너무 급하게 진행됐구나" — 감으로만 하던 완급 조절이 데이터로 보임 |
| **복귀 순간** | 몇 주 쉬었다 돌아와도 관계도·타임라인만 보면 3분 안에 작품 전체가 복기됨 | "노션이었으면 문서 20개를 다시 읽어야 했다" |

### 아하 모먼트 도달 설계 (Time-to-Value)
- 회원가입 없이 로컬 저장으로 즉시 시작 → 첫 관계도까지 **5분 이내** 목표
- 온보딩에서 "인물 2명 + 관계 1개"만 입력하면 즉시 관계도 미리보기 제공
- 빈 화면 대신 예시 작품(샘플 관계도·타임라인)을 먼저 보여줘서 완성형을 미리 체험시킴

## 3. 궁극적 가치 (Ultimate Value Proposition)

StoryVital이 최종적으로 제공하려는 가치는 기능의 합이 아니라 다음 세 층위다.

### ① 창작자의 "두 번째 뇌" — 기억의 외주화
연재가 길어질수록 작가의 인지 부담은 스토리 창작이 아니라 **설정 기억**에 소모된다. StoryVital은 인물·관계·사건·시간의 기억을 대신 맡아, 작가가 인지 자원을 온전히 "다음 이야기"에만 쓰게 한다.
→ *"설정은 StoryVital이 기억한다. 작가는 이야기만 쓴다."*

### ② 연재의 안전망 — 일관성이 곧 독자 신뢰
장편 연재물의 치명상은 필력 부족이 아니라 **설정 붕괴**다(인물 나이 오류, 죽은 인물 재등장, 시간선 모순). 이런 사고는 독자 신뢰와 작품 몰입을 한 번에 무너뜨린다. StoryVital은 관계도와 타임라인을 통해 모순을 연재 **전에** 드러내는 안전망이 된다.
→ 궁극적으로는 "설정 충돌 자동 감지"까지 나아가, 작가의 실수를 시스템이 막아주는 단계를 지향한다.

### ③ 설정의 자산화 — 기록이 곧 IP
StoryVital에 쌓인 인물·관계·세계관·타임라인은 그 자체가 구조화된 **IP 설정집(Story Bible)**이다. 연재를 위해 기록한 것이 그대로 2차 창작·영상화·게임화 피칭 자료가 된다.
→ PRD v2의 IP Bible 인증(₩49,000) 모델이 이 가치 위에서 작동한다: "기록하며 연재했더니, 팔 수 있는 기획서가 남았다."

### 한 문장 정의
> **StoryVital은 연재물 작가의 설정 기억을 대신 짊어지고, 작품의 일관성을 지켜주며, 그 기록을 판매 가능한 IP 자산으로 바꿔주는 서비스다.**

## 4. 문제 정의

연재물 창작자가 겪는 문제 (PRD v2에서 검증된 내용 유지):

1. **산재된 정보** — 설정 자료가 메모장, 구글 문서, 노션에 흩어져 있다.
2. **일관성 붕괴** — 연재가 길어질수록 초반 설정과 후반 전개가 충돌한다. (인물 나이, 사건 순서, 관계 변화 등)
3. **관계·시간의 복잡도** — 등장인물이 많아지면 "누가 누구와 어떤 사이인지", "이 사건이 그 사건보다 먼저인지"를 텍스트만으로 추적하기 어렵다.
4. **기존 도구의 한계** — 노션은 창작 특화 구조가 없고, 전문 도구(Scrivener 등)는 비싸고 진입장벽이 높으며, AI 생성 도구는 체계적 관리가 안 된다.

## 5. 타겟 사용자

| 타겟 | 특징 | Pain Point |
|---|---|---|
| 웹툰 작가 / 스토리 작가 | 연재물 제작, 회차 단위 작업 | 회차가 쌓일수록 설정·관계 추적 불가 |
| 웹소설 작가 | 장편 연재, 다수 인물 | 인물 관계와 시간선 관리 부담 |
| 작가 지망생 | 아이디어는 많지만 정리가 안 됨 | 어디서부터 구조화할지 모름 |

## 6. 핵심 기능

### 6.1 캐릭터 DB (등장인물 상세 기록)
- 인물별 프로필: 이름, 역할(주연/조연/단역), 성격, 외형, 배경 서사
- 인물별 **배경(백스토리)** 전용 기록 영역
- 검색·필터 (프로토타입에 하이라이트 검색 구현됨)

### 6.2 관계 & 친밀도 시각화 ★ 차별화 핵심
- 인물 간 관계 정의 (가족, 연인, 적대, 협력 등 관계 유형)
- 관계별 **친밀도 수치/단계** 기록 — 시간(회차)에 따른 변화 추적
- 관계도 그래프 시각화 (D3.js 또는 Cytoscape.js 예정)

### 6.3 사건 타임라인
- 작중 사건을 **발생 시간 기준**으로 기록·정렬
- 회차(챕터) 타임라인과 작중 시간선을 구분해서 관리
- 사건 ↔ 등장인물 연결 (누가 이 사건에 관여했는지)

### 6.4 챕터(회차) 트래커
- 회차별 진행 상태, 회차에 등장하는 인물/사건 연결
- 연재 진행률 관리

### 6.5 세계관 구축 (Worldbuilding)
- 시대, 장소, 핵심 룰, 분위기 등 세계관 설정 (Stitch 디자인 초안: `design/stitch/worldbuilding/`)
- 단순 기록을 넘어 세계관 요소 ↔ 인물/사건 연결로 확장 예정

### 6.6 라이브러리 → 스토어 (장기 구상)
- 1차: 내 스크립트·세계관·템플릿 보관함 (Stitch 디자인 초안: `design/stitch/library/`)
- 2차: **창작자 간 스크립트/세계관을 사고파는 마켓플레이스**로 확장
  - 잘 만든 세계관 설정집 자체가 거래 가능한 자산이 됨 — "설정의 자산화"(3장 ③) 가치의 마켓 버전
  - PRD v2의 WT 전략에 따라 저작권 분쟁 리스크가 있으므로 Phase 3 이후로 보류

### 6.7 내보내기
- JSON 백업 / 내보내기 (구현됨)
- 추후: 피칭용 PDF (IP Bible — PRD v2의 수익 모델과 연결)

## 7. UI/UX 방향

- **디자인 시스템**: "The Digital Nocturne / Neon Scriptorium" — [DESIGN_SYSTEM.md](./DESIGN_SYSTEM.md) 참고
  - 다크 테마 기반, 경계선 대신 톤 레이어링, 글래스모피즘, 네온 퍼플 액센트
  - Google Stitch로 뽑은 시안이 `design/stitch/`에 페이지별로 정리되어 있음
- **직관성 최우선**: 기록한 데이터가 자동으로 관계도·타임라인으로 렌더링되어, 읽지 않고 **보는** 것만으로 파악 가능해야 함

## 8. 기술 스택

| 영역 | 선택 | 상태 |
|---|---|---|
| 프론트 | 순수 HTML/CSS/JS (페이지별 단일 파일) | 프로토타입 구현 중 |
| 저장소 | localStorage (1차) → Firebase Firestore (동기화) | firebase.js 모듈 골격 작성됨 (설정값 미입력) |
| 인증 | Firebase Auth (Google 로그인) | 골격만 작성됨 |
| 호스팅 | Cloudflare Pages (예정) | 미배포 |
| 시각화 | D3.js 또는 Cytoscape.js (관계도) | 미착수 |

Firestore 데이터 구조(설계됨): `users/{uid}/works/{workId}/characters/{charId}`, `.../chapters/{chapId}`

## 9. 수익 모델 (PRD v2 계승)

Free(로컬 저장) → BYOK(본인 AI API 키) → Premium ₩9,900/월(클라우드 동기화, 관계도 자동 생성) → Pro ₩29,900/월(협업) + IP Bible 인증 ₩49,000(1회). 상세는 [PRD v2 docx](./StoryVital_PRD_v2.docx) 6장 참고. `prototype/pricing.html`에 요금제 페이지 초안 있음.
